## 1. Qué se hizo (y qué no)

Se reemplazó Firebase Auth por Supabase Auth en el flujo de login y protección de rutas, sin tocar:
- Firestore (`data-firestore.js` sigue leyendo/escribiendo ahí, tal cual).
- La lógica de negocio del backend (`resumenCfdi`, timbrado, Fiscalapi).
- El diseño, HTML/CSS o la experiencia de usuario del login/dashboard.

Los 6 objetivos de aceptación de la OT se cumplieron:
1. Firebase Auth reemplazado por Supabase Auth, sin tocar lógica de negocio.
2. Mismo flujo: login → dashboard protegido → logout → login.
3. `firebase-config.js` sustituido por `supabase-config.js` (para lo que toca a Auth).
4. Middleware del backend (`verifyAuth`) ahora valida JWT de Supabase.
5. Firestore intacto — cero migración de datos en esta OT.
6. Este documento cubre pruebas y rollback (secciones 4 y 5).

## 3. Diferencias de comportamiento a tener en cuenta

No son errores, son diferencias reales entre cómo funciona Firebase Auth y Supabase Auth — documentadas para que nadie las reporte como bug:

- **Login con Google:** Firebase abría una ventana emergente (`signInWithPopup`). Supabase redirige la página completa a Google y de regreso a `dashboard.html` (`signInWithOAuth`). El usuario ve una navegación en vez de un popup.
- **Mensajes de error:** Firebase daba códigos exactos (`auth/wrong-password`). Supabase da texto libre (`"Invalid login credentials"`), así que el mapeo a mensajes en español es por coincidencia de texto, no por código — si Supabase cambia el texto exacto de un mensaje en una actualización, el mapeo de ese caso dejaría de reconocerlo (seguiría mostrando el mensaje genérico, no rompería el login).
- **"Recordar sesión":** se preservó el mismo checkbox y el mismo efecto (localStorage vs sessionStorage), pero implementado con un adaptador de storage propio, no con una función nativa de Supabase equivalente a la de Firebase.

## 4. Pasos de validación

**Requisito antes de probar:** en Supabase (`contateck-dev`) debe existir al menos un usuario real de Auth con su `perfiles` vinculado (ya tienes 2 de la prueba de RLS de OT-0003 — sirven para esto también).

1. **Configurar variables del backend:** en `.env` (local) o Railway, agregar `SUPABASE_URL` y `SUPABASE_SERVICE_ROLE_KEY` (Project Settings → API → "service_role", es secreta, nunca va al frontend).
2. **Instalar dependencia nueva:** dentro de `backend/`, correr `npm install` (para traer `@supabase/supabase-js`).
3. **Arrancar el backend:** `npm start`. En consola debe aparecer si Supabase quedó "conectado" o no (mismo patrón que ya ves con Firebase). También se puede confirmar entrando a `GET /` — debe verse `"supabaseAuth": "conectado"`.
4. **Login de correo/contraseña:** abrir `login.html`, entrar con `prueba1@contateck.mx` (el usuario que ya creaste) → debe llevar a `dashboard.html` sin bloquear.
5. **Protección de ruta:** abrir `dashboard.html` directo, sin login previo (en una ventana de incógnito) → debe redirigir a `login.html`.
6. **Logout:** dar clic en cerrar sesión → debe volver a `login.html`, y al intentar abrir `dashboard.html` de nuevo, debe volver a pedir login.
7. **Backend con auth real:** con `REQUIRE_AUTH=true`, llamar a un endpoint de `/api/*` sin token → debe responder `401`. Con el `access_token` de una sesión real de Supabase en el header `Authorization: Bearer <token>` → debe pasar y `req.user.uid` debe coincidir con el `id` del usuario en Supabase.
8. **Firestore intacto:** confirmar que `dashboard.html` sigue mostrando los datos de pólizas/CFDIs/empleados igual que antes de este cambio (viene de `data-firestore.js`, que no se tocó).

## 5. Procedimiento de rollback

Si algo falla y hay que volver a Firebase Auth de inmediato, son cambios reversibles porque no se borró nada:

1. **Frontend:**
   - En `login.html`: regresar `<script src="firebase-config.js"></script>` en vez de `supabase-config.js`, y quitar el `<script src="supabase-config.js">` de `dashboard.html` (dejar solo `firebase-config.js`, como estaba).
   - Restaurar las versiones anteriores de `auth-login.js` y `auth-guard.js` (están en el historial de git, commit anterior a esta OT).
2. **Backend:**
   - En `backend/src/routes/invoices.js`, regresar la línea de import a:
     ```js
     import { verifyAuth, saveCfdi, markCfdiCancelled } from '../firebase.js';
     ```
   - No es necesario borrar `supabaseAuth.js` ni la dependencia `@supabase/supabase-js` — con revertir esa única línea de import, el backend vuelve a usar el middleware de Firebase.
3. **Con git, todo esto es un solo comando** si el rollback se hace antes de mezclar a `dev`:
   ```powershell
   git checkout dev -- frontend/login.html frontend/dashboard.html frontend/auth-login.js frontend/auth-guard.js backend/src/routes/invoices.js
   ```
   (esto trae de vuelta la versión de esos archivos que había en `dev` antes de esta rama, sin afectar nada más).
