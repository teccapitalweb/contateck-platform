## 0. Corrección de alcance importante

`empresas` y `perfiles` **nunca existieron en Firestore**. Se verificó directamente en el código: las únicas colecciones reales en Firestore son `polizas`, `cfdis`, `empleados`, `clientes`, `productos` (`data-firestore.js`). El selector de empresa del dashboard usa un arreglo fijo en `frontend/data.js` (`var EMPRESAS = [...]`), y los perfiles de usuario nunca tuvieron un documento propio — la identidad venía solo de Firebase Auth (ahora Supabase Auth).

**Consecuencia para los criterios de aceptación de la OT:**
- El criterio *"Firestore deshabilitado únicamente para los módulos migrados"* **no aplica** a `empresas`/`perfiles` — no hay nada de Firestore que deshabilitar para estos dos módulos, porque nunca vivieron ahí.
- Lo que sí aplica, y es lo que se hizo en esta Fase A: **conectar por primera vez** el sistema a las tablas Postgres reales (creadas desde OT-0002/OT-0003, con RLS ya probado), que hasta hoy existían pero no las usaba ni el backend ni el frontend.
- El arreglo local `EMPRESAS` de `data.js` cumple aquí el mismo papel que pedías para "Firestore como respaldo": sigue existiendo, sin tocarse, como red de seguridad si Postgres no responde.

## 1. Qué se construyó (Fase A)

1. **Acceso a Postgres desde el backend**, respetando RLS de verdad: las consultas se hacen con un cliente de Supabase autenticado como **el propio usuario** (su `access_token` + la `anon key`), nunca con la service role. Esto significa que si RLS le niega algo a un usuario, esta capa también se lo niega — no hay atajo que se salte la seguridad que ya construimos en OT-0003.
2. **Servicio/repositorio** (`backend/src/supabaseData.js`): función `obtenerEmpresaYPerfil(accessToken)` que trae el perfil del usuario y su empresa desde Postgres. Si algo no existe o falla, devuelve `null` — nunca lanza un error que tumbe la petición.
3. **Endpoint nuevo** `GET /api/perfil` (`backend/src/routes/perfil.js`), protegido por el mismo `verifyAuth` de OT-0004. Responde:
   - `{"ok":true,"fuente":"postgres","empresa":{...},"perfil":{...}}` si hay datos reales en Postgres.
   - `{"ok":true,"fuente":"local","empresa":null,"perfil":null}` si no los hay — señal explícita para que el frontend siga con su respaldo local.
4. **Frontend** (`auth-guard.js`): después de confirmar la sesión, consulta `/api/perfil`. Si la fuente es `"postgres"`, reemplaza el texto del selector de empresa (`[data-empresa-label]`) con el nombre real. Si falla o no hay datos, **no hace nada** — el dashboard sigue mostrando exactamente lo mismo que mostraba antes de esta OT (arreglo `EMPRESAS` de `data.js`).

**Nada se borró.** `data.js`, el selector de empresas en `app.js`, y toda la lógica existente siguen intactos.

## 3. Pasos de validación

1. **Backend:** agregar `SUPABASE_ANON_KEY` al `.env` local (Supabase → Project Settings → API Keys → pestaña "Legacy" → `anon` `public`, o la nueva "Publishable key"). Reiniciar `npm start`.
2. Confirmar en `GET http://localhost:8080/` que aparezca `"postgresData":"conectado"`.
3. **Vincular tu usuario de prueba a un perfil real** si no lo tienes ya (esto ya lo hicimos en OT-0003 con `prueba1@contateck.mx` → empresa `...0001`).
4. Con el backend local corriendo y `app-config.js` apuntando a `http://localhost:8080` (mismo truco de OT-0005), entra al dashboard logueado como `prueba1@contateck.mx`.
5. El selector de empresa debe mostrar **"TEC CAPITAL Group (DEV)"** (el nombre real que sembramos en `seed.sql`), no el "TEC CAPITAL Group" genérico del arreglo local — esa diferencia de texto es justamente la prueba de que sí está leyendo de Postgres.
6. **Prueba de respaldo:** con `app-config.js` sin `BACKEND_URL` (apuntando a producción, que todavía no tiene estas rutas nuevas desplegadas) o con el backend local apagado, el dashboard debe seguir funcionando normal, mostrando el nombre de empresa del arreglo local — sin errores visibles para el usuario.
